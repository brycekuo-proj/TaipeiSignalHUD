## 北北基道路號誌資訊 HUD 與實測學習系統

> 專案總覽 README｜更新日期：2026-09-30

## 1. 專案是什麼？

**青紅燈（TaipeiSignalHUD）** 是一套為道路駕駛情境設計的「前方紅綠燈資訊儀表＋資料蒐集與持續校正系統」。它希望讓使用者在手機主畫面或浮動 Overlay 中，直覺看見目前行駛道路、GPS 時速、前方適用路口、預估號誌燈色及剩餘秒數，並搭配固定測速、區間測速與科技執法提醒。

一般導航主要回答「怎麼到達目的地」，青紅燈的核心問題則是：「**我目前真正位於哪一條道路？沿行進方向的下一個適用號誌在哪裡？目前能提供多可靠的號誌資訊？**」

專案不只開發 Android App，也建立一套在 Mac 上運作的 MCP 資料接收、路網匹配、官方資料整合、Camera／Bus／CCTV 輔助觀測、號誌時相學習和自動校正流程，使實際道路使用者的觀測逐步改善資料品質。

**重要定位：本產品是輔助資訊 HUD，不是官方即時 SPaT 服務、不取代導航，也不代替駕駛人的判斷。現場號誌、道路標誌及交通指揮永遠優先。**

## 2. 要解決的實際問題

1. **路口抓錯：** 單靠 GPS 距離選最近紅綠燈，可能跨過多個實際路口，或選中平行道路、巷弄、反向道路的號誌。
2. **道路層級混淆：** 在高速公路、高架、快速道路、地下道、匝道入口或出口時，手機位置在平面投影上與下方道路重疊，容易抓到不適用的紅綠燈。
3. **資料覆蓋不足：** 台北市外的新北市、基隆市部分路口可取得位置，卻未必具有可用、可靠的即時燈色及倒數秒數。
4. **時相偏移：** 即使具有號誌時制，也可能因同步基準、方向、時段切換或臨時控制造成固定數秒或更大的誤差。
5. **畫面與更新延遲：** 主畫面與 Overlay 不能各自維護一套互相衝突的 GPS／倒數邏輯；速度、路名、燈態與警示應由同一個資料狀態同步更新。
6. **長期維護成本：** 需要利用實測自動發現異常、校正資料、保存有價值的成果，避免原始 Logger 紀錄無限制占用 Mac 硬碟。

## 3. 主要用途

### 3.1 駕駛端：Android HUD

- 顯示目前 GPS 車速與所匹配的道路名稱、行駛方向。
- 顯示目前／下一適用路口；在需要時提供沿路網往前排序的候選號誌。
- 以**單顆可隨紅、黃、綠變化的圓形燈號**顯示主要號誌，圓內顯示可信的預估倒數秒數；無法可靠判定時顯示「--」。
- 主畫面與 Overlay 同時接收同一個位置、號誌及警示狀態，不必開啟 Overlay 才開始計時。
- Overlay 可調整透明度及拖曳位置，目標是在使用其他地圖時盡量不遮擋路線。
- 依所在道路與行進方向顯示測速照相、區間測速、科技執法資訊；提醒距離可設定。
- 提供一般道路、快速道路與高速道路分開設定的車速提醒（規劃預設分別為 60／80／100 km/h；使用者可自行調整）。
- 以簡潔、容易在短時間辨識的介面為原則，避免堆滿導航式資訊。

### 3.2 蒐集端：SignalLogger／Camera

- Android 手機在道路測試時蒐集 GPS／GNSS、時間戳、速度、航向、定位精度及可用感測器資料。
- 先存入手機本機資料庫，之後分批上傳 MCP；網路中斷時保留資料，復線後以批次、ACK 與去重方式補送。
- Camera 作為輔助觀測：辨識前方疑似紅／黃／綠燈，並結合 GPS、車輛方向、實際道路與路口匹配結果核對。
- 夜間、路燈、尾燈、反光及相鄰方向號誌均可能造成誤判，因此**看到某種顏色不等於已確認本車道的真實燈態**。
- 當 HUD 顯示「--」或與高可信 Camera／GPS 觀測發生衝突時，記錄證據、核對同一道路／同一路口／同一接近方向，再依可信度觸發即時修正或標記待驗證。

### 3.3 資料端：Mac MCP 學習與校正

- 收集 Android Logger 與 HUD observation，建立同時間、同方向、同路口的對照。
- 比較官方資料、歷史時相、Camera 識別、公車相關觀測與 CCTV 學習結果。
- 記錄原始誤差、修正後誤差、資料版本與校正依據，追蹤每輪是否真的改善。
- 建立信心分級；符合門檻時才能自動升級路口資料，而非因為觀測量增加便直接升級。
- 依規劃在原始 Logger 資料達 5 GB 時執行一輪分析、校正、報告與已處理原始資料清理；保留必要的聚合成果、校正紀錄及未完成事件。
- 初始階段以較密集的連續學習建立基礎資料，後續朝每週核對與校正的低維護模式發展。

## 5. 覆蓋範圍與道路判斷原則

**地域目標：台北市、新北市、基隆市。** 實際採用「建立完整號誌位置清單、優先補強主要幹道的可信號誌時間」策略。初期不以全台完整覆蓋為出貨條件。

道路／路口匹配不能只選 GPS 最近點，至少要綜合：

- 近期 GPS 軌跡、定位精度、航向、速度及可能的跳點。
- 道路幾何、方向、拓樸連通性與前方可到達路口的順序。
- 主線、側車道、平行道路、橋下道路的差異。
- OSM 等資料中的 layer、bridge、tunnel、oneway、junction、link，以及官方道路資料。
- 高架、快速道路、高速公路、地下道及匝道的**入口通過／持續行駛／出口切換狀態**。
- 真正進入出口匝道後，才合理搜尋出口端下一顆適用號誌；不可憑平面距離抓下層道路號誌。
- 橋梁不一律視為受限特殊道路：是否需要分層判斷，應依實際路網結構與行車動線決定。

選擇結果需要區分「道路位置可信」和「號誌時間可信」兩件事：知道前方有燈，不代表知道它現在是什麼燈色。

## 6. 號誌可信度：C → B → A

| 等級 | 含義 | 使用方式 |
| --- | --- | --- |
| **C 級：位置覆蓋** | 確認號誌／路口位置及盡可能取得名稱、行進方向，但缺乏通過驗證的燈態與倒數。 | 可顯示適用路口；號誌倒數維持「--」，**不得編造顏色與秒數**。 |
| **B 級：可信的主要道路資訊** | 以官方時制／位置為基礎，配合公車、CCTV、實車等適用證據，通過方向、時段、同步與一致性門檻。 | 可在品質門檻內提供預估燈態／秒數，遇失步、動態號誌或異常時退回未知狀態。 |
| **A 級：較高驗證成熟度** | 同一路口在不同時段及多次獨立觀測中持續通過校正，且有可追溯的誤差與品質紀錄。 | 作為逐步提升精度與覆蓋率的後續目標，並非保證與現場永遠零誤差。 |

**B 級是目前發展關鍵：** 先補足主幹道可見、可用的資訊，再邀請計程車／Uber 等更多道路使用者加入測試。使用者增加後，Logger 才能蒐集更廣泛的實際行車資料，逐步改善 A 級覆蓋。不得把未驗證的 C 級資料偽裝成 B／A 級。

## 7. 主要資料來源與整合原則

1. **臺北市：** 交通相關開放資料、號誌位置／時制、交通資訊服務、測速及科技執法公開資料。
2. **新北市：** ATIS、開放資料平台、官方號誌 ID 與位置、交通及公車資料。
3. **基隆市：** 市府交通／開放資料、可確認的路口位置與相關公車資料。
4. **OpenStreetMap（OSM）：** 北北基道路幾何、方向、複雜路網與 traffic_signals 節點；使用及再散布需遵守 ODbL 授權與標示。
5. **公車／TDX 等資料：** 補充路線、行經路段及可用的交通觀測；公車動態本身不能直接當作號誌真值。
6. **道路 CCTV：** 按基隆 → 新北 → 台北的順序研究主要道路可用影像與號誌時相；須檢查視角、相機時間、畫面更新率、遮擋與燈號歸屬。
7. **實車資料：** Android GNSS、Camera 與 HUD 比對事件，用以校正官方位置、時相偏移和路網選取模型。

## 8. 即時判定與學習閉環

1. 手機取得 GNSS、時間、速度、航向、定位精度。
2. 由道路拓樸與近期行車軌跡確認所在道路／層級，不依賴最近道路的單點猜測。
3. 預測前方實際可到達的適用路口，排除反向、鄰近巷道、橋下等不相關號誌。
4. 查詢官方資料、已同步時相與可用的學習成果，計算燈態及預估剩餘秒數。
5. 加上資料等級、有效時間與一致性檢查，將同一份狀態更新至主畫面及 Overlay。
6. Camera、OPPO Logger 與其他觀測持續回傳；若 HUD 為「--」或發生紅燈／綠燈衝突，先驗證路口、車道適用性、方向、時間戳與影像可信度。
7. 證據充足時，更新可用快照或修正模型；未達門檻時記錄待驗證事件，不因單次影像或「車在移動」就直接覆寫燈態。
8. MCP 定期歸納失敗原因，例如位置偏移、方向錯誤、時制不同步、Camera 誤辨及公車／CCTV 來源不足。
9. 每次校正應保存修正前後誤差欄位（before_error_sec／after_error_sec）、樣本量與版本資訊，確認成效後才可發布。
10. 執行 5 GB 維護時，完成分析及結果持久化後才清理已處理原始紀錄；不得刪除仍在使用的資料、必要溯源或校正報告。

**目前不承諾：** 所有路口均有即時相位、所有路段均準確、所有 CCTV 均能看到適用號誌，或車輛移動即可證明前方一定綠燈。資料不充分時，寧可顯示未知。

## 10. 使用情境與測試流程

### 測試設備的角色

- **OPPO 手機／車機：** 長時間 Logger、GNSS 與 Camera 輔助觀測。
- **Samsung A37：** 主要 HUD／Overlay 道路實測。
- **Samsung A16 等 Android 設備：** 相容性與補充驗證。
- **Mac mini：** MCP 接收器、SQLite、資料整合、學習程序及校正報告。

### 一次實車驗證應確認

- 手機定位與 Mac MCP 連線是否穩定，網路中斷後是否能補送。
- 行經路名、方向、路口排序是否符合真實車道及行駛路徑。
- 平面道路與高架／快速／國道／匝道是否正確區分。
- 主畫面和 Overlay 的車速、倒數、燈態是否同步。
- Camera 判斷的燈色是否真的對應到本車輛的適用號誌。
- 預估燈色／秒數與現場資料的差異；不確定時是否安全退回「--」。
- 執法提醒是否位於**同一行車路段與適用方向**，避免隔街誤報。
- 測試完成後，是否有可追溯的 observation、異常事件及校正報告。

## 12. 隱私、資料治理與安全

- 原始 GPS 軌跡、Camera 觀測與測試資料僅用於授權的道路學習／品質校正，避免不必要的人員或車牌影像蒐集。
- 存取權杖、MCP 認證資料、Tunnel 機密與本機環境設定不寫入 README、不提交 Git。
- 優先上傳必要的結構化事件與短期觀測，不以長期保存完整影像作為預設。
- 個別資料需可標示來源、時間及品質；建立保留期限、分析後清理和例外保留規則。
- 定時校正只發布經驗證的成果。任何推算均須能撤回到上一版或降級成未知。
- 行車測試應遵守交通法規，裝置須固定，勿在駕駛行進中操作畫面。
- 畫面提示為輔助參考，不可據此闖燈、加速搶秒或忽略現場號誌。

## 13. 發展路線

**階段一｜建立可用基礎：** 北北基號誌主表與路網、C 級位置覆蓋、Android 共用狀態服務、Logger→MCP 的可靠資料流。

**階段二｜B 級主要道路：** 基隆 CCTV／Bus 學習先行，接續新北、台北；以官方資料與實車證據驗證主要幹道的路口位置、方向、燈態和預估秒數。

**階段三｜擴大道路測試：** 在 B 級資料可靠性達到可見的門檻後，再邀請小黃、Uber 等高頻道路使用者加入測試；依實際資料量評估伺服器與 VPS 頻寬，而非過早增加固定成本。

**階段四｜向 A 級迭代：** 更多實車資料 → 更廣的時段、路口與路型驗證 → 自動發現偏差 → 可追溯校正 → 更新 App／MCP 資料。持續降低未知率、錯路口率及倒數誤差。

衡量成功不只看「收集了多少影像或 Logger 筆數」，更應追蹤：正確路口匹配率、可用 B 級路口比例、倒數校正前後平均／分位誤差、Camera 有效樣本率、誤報率，以及主畫面和 Overlay 的更新穩定性。

---

**一句話總結：青紅燈希望透過官方與開放交通資料，加上 Android 實車、Camera、Bus、CCTV 和 Mac MCP 的持續校正，打造一個以北北基主幹道為起點、能逐步提高可信度的前方道路號誌資訊 HUD。**
